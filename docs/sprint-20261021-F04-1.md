### HTTP-10 — the decompression limit is held only as a memory ceiling

What is not held: `parse_sitemap_xml` reads `SITEMAP_MAX_UNCOMPRESSED + 1` bytes out of a gzip stream, and the
two tests require the document invalid and the peak under 150 MB. A read of 60,000,001 (the review of 0.172.0)
stays green.

- **H10-a.** A gzipped urlset that expands to exactly 52,428,800 bytes parses as a `urlset` with its URL; one
  that expands to 52,428,801 is `invalid` naming the limit. Expected **green on `efce43e`** (the comparison is
  right); red under `>` → `>=` and under the constant set to 60,000,000.
- **H10-b.** Over a 200 MB expansion, the bytes the gzip reader hands back in total are at most 52,428,801 —
  counted by wrapping the reader, so the number tested is the limit's own, not memory. Expected **green on
  `efce43e`**; red under `read(60_000_001)`.
- Holds in full → `enforced`. No verdict moves.

### HTTP-13 — the `www.` variant is held for the crawl only

- **H13-a.** `sitemap_checker`, `indexability_matrix` and `--sample`'s fallback each request a sitemap on the
  `www.` variant of the audited host, and one under the other scheme, as the audited site's own (none named
  off-host). Expected **green on `efce43e`** (all three call `same_host` with its default); each red when that
  walker alone passes `include_www_variant=False`, or compares the scheme.
- **H13-b.** The Not-held paragraph's "one kind per result": SE-117 (`security_headers.py`, whose http
  variant's request the guard refused) and TE-167 (`domain_safety_check.py`, whose uptime request it refused)
  are `NO_DATA` by an absent key, with no `error_kind`, while the scenario says a file a script reads refused
  this way leaves the item it decides `NO_DATA` **with the kind `blocked`**. Expected **red on `efce43e`** for
  both rows; repaired by letting a script name the kind of a field it withheld, which the runner reads when
  that field is the one an item asserts on. Status unchanged (`NO_DATA`); `error_kind` and the evidence's
  label move from none to `blocked`. A CHANGELOG line, since the row reads differently in every report.
- **H13-c.** A crawled page that timed out is read as part of the crawl (the crawl is not `truncated` for
  it). That is not a refusal and not in HTTP-13's text; whether a clean site-wide verdict over a page that
  gave no answer should be withheld is `verdicts` VRD-14's question and moves live verdicts on slow sites.
  Not changed here: asked of the owner, filed under **Queue**.
- Holds in full for its own text → `enforced`.

### INP-10 — "only when it decided something" has no reader

- **I10-a.** The runner, given a property it derives from the bundled list (a name, Search Console
  credentials, no `--gsc-property`) and a snapshot older than `PSL_STALE_DAYS`, says on stderr that the list
  is old and how old. Expected **green on `efce43e`** once a test can reach the branch at all (no test can
  today: every fixture is an address).
- **I10-b.** The same run with `--gsc-property` says nothing about the list; with no credentials, nothing.
  Expected **green on `efce43e`**.
- **I10-c.** A snapshot whose date cannot be read, with the property derived from it: the scenario says the
  age is reported as unknown, never read as fresh. The runner warns only on `age > PSL_STALE_DAYS`, and an
  unknown age is `-1`, so it says nothing. Expected **red on `efce43e`**.
- **I10-d.** "Wherever the reader of that run can see it": the warning is on stderr only and the report,
  which is what gets handed on, does not carry it. Expected **red on `efce43e`**; repaired as a provenance row
  (`REP-3`), present only when the property was derived from the list.
- The mechanism the Reader line says the suite lacks — a fixture reachable by name inside the runner's own
  process — is a wrapper like `tests/entry_gate_off.py`: the real runner, with the name resolved to this
  machine and the host not taken for a private one. Holds in full → `enforced`. No verdict moves.

### EVD-10 — the unverified caveat reaches no report

- **E10-a.** A run with a server log and no `--verify-bots`: both reports say the crawler counts take the
  User-Agent at its word. Expected **red on `efce43e`** (`bot_identity` is read by nothing).
- **E10-b.** A run whose bots were verified does not carry that caveat. Expected **green** (vacuously red-free
  today; held once E10-a exists).
- Repaired as a provenance row (`REP-3`). Holds in full → `enforced`. No verdict moves.
