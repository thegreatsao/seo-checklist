### DEC-1 — a declaration is written before the run; held by nothing

The Reader line names the instrument that was never built: *the batch records what it was given*, and a gate could
refuse a batch whose input list holds a recording. Two things are buildable and one is not.

- **D1-a, the batch ledger.** The manifest gains `batches`: each names the declarations it wrote (origin, item) and
  `given`, the list of what the declaring session was handed. A gate walks history from an epoch (the commit that
  introduces the ledger; the 250 declarations before it carry no record and are not claimed) and refuses, in both
  directions, a declaration added after the epoch that no batch names, and a batch naming an addition that never
  happened. `given` is read against an allow-list built from what the requirement permits — the fixture material
  the harness serves (`FixtureSite.material()`) and the registry — so `tests/census.json`, this spec (its
  Appendix A), the manifest's `triage`, a transcript or a handoff are refused by not being on it. Expected: **on
  today's tree green and vacuous** (no addition after the epoch); **red on each mutation** — an added declaration
  with no batch, a batch whose `given` names `tests/census.json`, a batch naming a declaration that was not added.
- **D1-b, the order the oracle can witness.** `test_fixture_oracle.setUpModule` refuses to audit while the working
  tree's manifest declares an (origin, item) that `HEAD`'s does not: the module docstring's rule ("commit a new
  declaration before running anything here at all") is today a sentence. With it, the first comparison any new
  declaration meets is against a prediction git holds, and a revision after that run is a commit-to-commit move
  DEC-8's walk sees. Expected: **no such guard today** (a declaration added uncommitted is audited); red test first.
- **Narrowed, and filed:** whether a batch's `given` is the whole of what that session saw — a transcript, a run in
  another checkout, a census read the day before. No reader can establish what a person had not seen; the
  requirement keeps the obligation, the Reader line says it is the unheld part. Also not claimed: the 250
  declarations before the epoch.
- Expected after: `enforced` for the narrowed requirement, in DEC-7's form ("one narrowing … what it gives up is
  said"). No verdict moves.

### DEC-4 — a reason argues from the fixture; "names something the tree contains" is unread

- **D4-a.** A reason states the construction, so it names something the origin's tree contains: a served page or
  file by its path, or a literal (in backticks or quotes) that occurs in that origin's material. Expected: **most
  reasons do; some do not**, chiefly those arguing an absence ("the tree has no paginated series"), which can name
  the page that lacks the subject or nothing at all. I cannot say how many. **Decision rule, fixed now:** if every
  reason names something its tree contains, the reader requires it (strong form, which also refuses the
  scenario's "expected PASS because it passes", accepted today). If some do not, they are counted and listed under
  Outcome, the reader requires instead that **whatever a reason names exists in its origin's tree** (a reason
  naming a page its tree lacks argues from another fixture — the pasted-across-origins shape again), and the strong
  form is narrowed and filed.
- **D4-b.** A reason is not a note about the run: a `why` that speaks of the run, the audit's answer, the census or a
  report is refused. Expected: **a few hits** (the three declarations withdrawn and re-declared in Stage 2c are the
  likeliest). A hit is a manifest defect; its `why` is rewritten from the tree alone, and the rewrite is listed
  under Outcome (a `why` edit moves no `expect`, so DEC-8's walk does not see it — the Outcome is its record).
- Not held by any reader and narrowed out, filed: that the argument is true — that the construction named does
  produce the status.
- Expected after: `enforced` for the narrowed requirement if the mutations redden. No verdict moves.

### DEC-9 — the manifest's `registry_version` is a stamp a hand can set

The Reader line says the manifest copies nothing from the registry; since DEC-5 (0.93.2) it copies each declared
item's title, which is re-read. What it does not copy is the rest of what a declaration is reasoned from — the
item's rule (`check`).

- **D9-a.** Mutation: change a declared item's `check` in `checklist.json`, recompute the registry's version, and
  set the manifest's `registry_version` to it. Expected: **every reader of the manifest green** (the title is
  unchanged; the stamp agrees). Repaired by recording on each declaration a `basis`, a digest of the item's title and
  `check` through the generator's own `registry_version_of`, compared with the registry's item on every run. Then
  the stamp is not the whole check: a stamp moved onto declarations whose items moved reddens, and a stamp moved
  over a registry that changed only items nobody declared describes declarations that are, item for item, what
  they were — which is the honest case. Expected **red after the repair**. The bulk stamping is a recording, said as
  DEC-5's is: it makes the next move visible and claims nothing about the past.
- **D9-b.** The census: the same mutation with the census's stamp set. Expected: `tests/test_census.py` green (its
  copied fields are not `check`), and `verdict_census.py --check` (DEC-12, the CI `census` job) **red when the rule
  change moves any answer** — a re-taking is the census's reader for this, and the Reader line should say so.
- Expected after: `enforced`, both instruments. No verdict moves.
